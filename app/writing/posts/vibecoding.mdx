For the past few months I have been testing what people call "vibe coding": prompting a large language model to scaffold features, fix bugs, and iterate fast.

The appeal is obvious. You describe what you want, and a component or function appears. The longer I worked this way, the clearer the tradeoffs became.

## Speed Without Understanding

Skipping straight to prompts feels fast. You skip the docs, the breakpoints, the edge cases.

But speed without understanding is fragile. Hand all the problem-solving to a model and you slowly lose track of how your app works. When a subtle state bug or memory leak reaches production, you are debugging code you never really read.

> If you do not read and understand the code you commit, you are not building software — you are outsourcing your judgment.

Engineering is not typing lines. It is building a mental model of how a system behaves, fails, and scales.

## Use AI to Learn Faster

The shift that helped me was changing the question. Instead of asking for code, I started using the model as a pair programmer and a research assistant.

When I meet an unfamiliar library or algorithm, I ask:

- *Why this pattern or data structure here?*
- *What does it cost in performance or memory?*
- *How does this behave when the network fails?*
- *What are the alternatives, and what do they trade?*

Used this way, AI is a patient tutor. It shortens the path to understanding and sends me back to the official docs with better questions.

## Rules I Follow

1. **Read before committing.** Trace every path, check scopes, confirm error handling.
2. **Own the architecture.** Let AI draft boilerplate and experiments; keep data flow, domain models, and system design yourself.
3. **Write down what you learn.** Notes on new patterns and edge cases turn a quick session into lasting knowledge.

Tools will keep changing. Problem solving, curiosity, and clear thinking will not.
